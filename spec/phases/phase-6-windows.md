# Phase 6：Windows 集成与交接

上级：[requirements](../requirements.md)。依赖：Phase 1–5 工程交付；拟真证据不足需保留。落实 R11、R12、R14。

## 实现

- doctor 预检、Windows 可选依赖锁、配置样例、测试窗口执行器。
- 感知适配器输出带质量和时效的快照；接入已有路线时锁定参考版本。
- 执行所有直接输出收口审计，再开启 shadow 和测试窗口 execute。
- 按 [Windows 手册](../windows-validation.md) 完成故障矩阵、性能测量与证据打包。
- 用户提供实际硬件和地图配置，填写 manifest；结果反馈不包含不必要的私人输入。

## 验收

- [ ] 新 Windows 环境按文档能安装、运行 doctor、通过核心测试。
- [ ] shadow 模式零真实输出；execute 仅作用于明确选择的测试目标。
- [ ] 急停、失焦、捕获失效、异常、退出均验证释放流程。
- [ ] 10 分钟样本报告阶段耗时与资源占用，1GB 显存设备是否可用以报告为准。
- [ ] 至少一轮完整采集→校验→回放→模拟生成→评测→报告可重现。
- [ ] 形成 passed/failed/not_run 清单与未解决问题，更新 README 的已实现能力。

## 局域网部署验收

本地闭环通过后开发 RemotePolicyClient/服务端，使用 ActionProposal 协议返回短有效期按键组合。本机保留感知、校验、调度和急停，模型机加载权重。认证、请求关联、epoch、消息限额、期限检查与断线停止一起交付。

验收：延迟、乱序、重复响应、断网、服务重启、会话串线不能执行旧提案或重复 tap；跨机单调时钟不直接比较。记录 RTT 与捕获到输出总延迟，比较本地和远端动作一致性。没有第二台机器时标未运行，本地可独立验收，不能声称两机验证通过。

## v0.3 应用交付与验收（R17、R18）

用户通过原 run_gui.py/UI 使用四种模式，真实执行复用原 InterceptionController；训练/评测 CLI 是辅助工具，共用同一控制器适配器。验证驱动可用性、键名归一化、原配置兼容、错误回执和最终释放。

验收：原入口能启动、F4 不被新演示录制替代、四模式输出边界正确；模型正常操作由同一 Interception 后端执行。驱动不可用时 model_control 禁止启动，manual_record/shadow 可用且不初始化输出。使用测试窗口验证显式时长不被二次随机，驱动失败不能记成功回执。
